# Render staging deployment checklist

A step-by-step guide to running Quillvora on Render in **Stripe test mode** before any
paid launch. Nothing here has been done yet; each step needs the owner's approval
because it creates paid hosting or touches Stripe.

> Cost warning: `render.yaml` creates a **paid** `starter` web service plus a 1 GB
> persistent disk (a disk requires a paid instance). Check Render's current pricing
> before step 2. Suspend or delete the service when you are not testing.

## 0. Before you start (free, local)

1. All tests pass: `PYTHONPATH=. pytest -q` (CI also runs these on every push).
2. GitHub Actions is green for the branch you will deploy (it builds the Docker image
   and checks `/health`).
3. Have ready (test mode only — keys start with `sk_test_`, never `sk_live_`):
   - Stripe test secret key, and the three test price IDs listed in
     `STRIPE_SANDBOX_TEST_PLAN.md`.
   - A Resend API key and a sender address on a domain verified in Resend.
   - A Fernet key for `API_KEY_ENCRYPTION_KEY` (command in `.env.example`). Store a
     copy in your password manager.

## 1. Choose what to deploy

Render deploys a branch. For staging, deploy `fix/production-readiness-p0-final`
(or `main` after the PR is merged). `autoDeploy` is off, so nothing redeploys
without you clicking **Manual Deploy**.

## 2. Create the service (incurs cost — owner approval required)

1. Render Dashboard → **New → Blueprint** → select this repository and branch.
2. Render reads `render.yaml` and asks for every value marked `sync: false`.
   Fill them in using `.env.example` as the reference:

   | Variable | Staging value |
   | --- | --- |
   | `STRIPE_SECRET_KEY` | `sk_test_...` |
   | `STRIPE_WEBHOOK_SECRET` | leave blank for now (step 4) |
   | `STRIPE_PRICE_STARTER` / `_PROFESSIONAL` / `_BUSINESS` | test price IDs |
   | `API_KEY_ENCRYPTION_KEY` | your Fernet key |
   | `RESEND_API_KEY`, `FROM_EMAIL` | Resend key and verified sender |
   | `CHECKOUT_SUCCESS_URL`, `CHECKOUT_CANCEL_URL`, `CUSTOMER_PORTAL_RETURN_URL` | e.g. `https://<service>.onrender.com/dashboard` |

   `API_ADMIN_KEY` is generated by Render automatically. `CORS_ORIGINS` may stay empty
   unless a separate website calls the API from a browser.
3. Apply. The first build takes a few minutes.

## 3. Verify the deployment

Replace `<url>` with the `https://...onrender.com` address Render shows.

```bash
curl https://<url>/health        # expect {"status":"ok","service":"quillvora-api"}
curl https://<url>/              # service info
```

Also open `https://<url>/docs` in a browser.

Staging checks still outstanding from the PR:
- **Disk ownership:** `/health` returning `ok` proves the app can write to the
  database on `/var/data`. Restart the service and confirm a key created before
  the restart still works (data persisted).
- **Forwarded IP/HTTPS:** response headers should include `Strict-Transport-Security`
  (proves the app sees HTTPS behind Render's proxy). Hit
  `/v1/billing/recovery/request` six times within an hour from one machine, using a
  different email each time (each email also has its own limit of 3), and confirm
  the sixth returns 429 (proves per-client IP throttling is not using
  Render's proxy IP for everyone).

## 4. Connect the Stripe test-mode webhook

1. Stripe Dashboard (**Test mode** toggle on) → Developers → Webhooks → Add endpoint.
2. URL: `https://<url>/v1/billing/webhook`
3. Select only these events (the ones the app handles):
   - `checkout.session.completed`, `checkout.session.async_payment_succeeded`
   - `customer.subscription.updated`, `customer.subscription.deleted`,
     `customer.subscription.paused`, `customer.subscription.resumed`
   - `invoice.paid`, `invoice.payment_failed`
   - `charge.refunded`, `charge.dispute.created`, `charge.dispute.updated`,
     `charge.dispute.closed`
4. Copy the endpoint's signing secret (`whsec_...`) into Render's
   `STRIPE_WEBHOOK_SECRET`, save, and redeploy.
5. Send a test event from Stripe; the endpoint should answer 200. A request without a
   valid signature must answer 400.

## 5. Run the Stripe sandbox lifecycle

Follow `STRIPE_SANDBOX_TEST_PLAN.md` scenario by scenario using Stripe test payment
methods only. Record evidence as that document describes.

## Refunds and disputes: manual review

A `charge.refunded` or `charge.dispute.*` event places an access hold on every key
for that Stripe customer. `subscription_status` keeps showing Stripe's real status;
the hold is stored separately and no Stripe event removes it. Review and clear
holds with the admin API — see `ADMIN_GUIDE.md`.

## Not covered yet (blocks paid launch)

- Offsite SQLite backups and a tested restore (`BACKUP_RUNBOOK.md`).
- Monitoring/alerting (e.g. Render health alerts, error notifications).
- Switching to live Stripe keys, a live webhook, and real price IDs — only after
  every staging scenario passes and the legal drafts are approved.
